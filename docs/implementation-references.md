# Ориентиры реализации Courier

Это результаты исследования соседних проектов и выбранные подходы Courier.
Текущая реализация и эксплуатационные параметры описаны в [runtime.md](runtime.md).

## PostgreSQL в Komeet

Исследован `naukograd-software/komeet/services/komeet`, а не `services/old`.

| Область | Текущая реализация |
| --- | --- |
| SQL | `internal/infrastructure/postgres/schema.sql` и `queries/*.sql` |
| Генерация | `sqld.yaml`: `sqld-gen-go` → `gen/db`, nullable через указатели, UUID через `google/uuid.UUID` |
| Версии | Генераторы `sqld` v1.1.3 в Makefile, runtime-зависимость `sqld` v1.0.0 в Go-модуле |
| Соединения | `postgres.New`: настраиваемый `pgxpool`, стартовый Ping, закрытие при ошибке и остановке |
| Транзакции | `pgtx.NewTxManager`, `pgtx.NewTxDB`; репозитории получают `tx.DB`, передаваемый в generated `db.New` |
| Граница операции | Например, `internal/api/timeline.go:SendMessage` использует `tx.DoReadCommittedRet` |
| Миграции | SQL встроен в бинарник; `ApplyMigrations` передаёт миграции приложения и `pg-outbox` в `sqld/migrate` |
| Телеметрия | pgx tracing, статистика пула, `queryLogger` скрывает SQL-аргументы |
| Проверки | Настоящий PostgreSQL; часть DB-тестов пропускается без `KOMEET_TEST_PG_DSN` |

В конфигурации включён только Go-плагин. Makefile всё ещё устанавливает
Bob-генератор и упоминает `gen/bob`; это не действующая конфигурация.

`queries/timeline.sql:ClaimDueScheduled` использует `FOR UPDATE SKIP LOCKED`.
Обработка отложенного сообщения и удаление строки происходят в одной
транзакции. Для внешних SMTP/HTTP-вызовов Courier нужен другой жизненный цикл:
короткая транзакция захвата, отправка вне неё, затем условное завершение
по идентификатору действующего захвата.

## OpenAPI и SDK в IAM

- Источник контракта — `openapi/openapi.yaml` (OpenAPI 3.1).
- `make generate-go` создаёт промежуточную OpenAPI 3.0-схему через
  `scripts/openapi_to_30.py`, затем запускает ogen v1.20.3.
- Go-клиент и серверные интерфейсы генерируются в `internal/oas`,
  недоступный внешним Go-потребителям IAM.
- `make generate-ts` использует `@hey-api/openapi-ts`; generated-код
  в `ts/packages/sdk/src/gen` экспортируется SDK-пакетом.
- Ручной TS-слой добавляет управление IAM-сессиями, которое Courier
  само по себе не требуется.
- CI проверяет актуальность generated TS через регенерацию и `git diff`.
  Аналогичного шага регенерации Go API и DB-кода в текущем CI нет.
- `pkg/sdk` предназначен для проверки IAM-токенов и не является образцом
  публичного сгенерированного HTTP-клиента Courier.

## Подход Courier

SQL-слой: `pgxpool` + `pgtx` + `sqld`, явные SQL-запросы, generated-модели,
параметры и результаты. Адреса, содержимое и секреты исключаются из DB-логов,
трасс и ошибок телеметрии. Миграции проверяются на пустой БД и на обновлении;
применённые миграции не переписываются.

Запись идемпотентности и заданий проходит через один транзакционный DB-адаптер.
Для очереди используется опубликованный `pg-outbox v1.1.0`. Схема его таблицы
импортируется из закреплённого Go-модуля при генерации sqld. Миграции Courier
включают этот снимок вместе с собственными таблицами; отдельное применение
миграций библиотеки не требуется. Правила уведомлений остаются в Courier.

### Возможности и границы pg-outbox

Подключённая версия —
[`pg-outbox v1.1.0`](https://github.com/gopherex/pg-outbox/releases/tag/v1.1.0).
При обновлении с v1.0 применяется миграция `0002_delivery_control.sql`;
старые воркеры останавливаются до запуска новой версии, поскольку они
ещё не проверяют токены захвата при записи результата.

`Publisher.Publish(ctx, []Message) error` поддерживает собственную реализацию
отправки. `Message.Payload` содержит сериализованные данные Courier, а
`Codec` позволяет использовать свои способы кодирования. Publisher может
декодировать задание, проверять предпочтения и срок действия, вызывать SMTP,
WebPush или FCM — публикация в отдельный брокер не обязательна.

Одно outbox-сообщение соответствует одной доставке в один канал.
`WithBatchSize(1)` устраняет повтор соседних успешных доставок при ошибке;
`WithConcurrency` сохраняет параллельное выполнение. Пакетный интерфейс
сам по себе не является причиной писать новую очередь.

Интеграция использует общие результаты publisher: `Permanent` для ошибки без
повтора, `RetryAfter` для минимальной задержки и `Discard` для завершения без
публикации. Courier сам классифицирует ошибки провайдера, проверяет expiry
и предпочтения. Технический `discarded` в библиотеке не содержит этих правил.

Библиотека продлевает захват при выполнении publisher и проверяет уникальный
токен попытки при завершении. Настраиваемая очистка payload выполняется вместе
с переходом в published/discarded; dead-записи имеют отдельный срок хранения.
Ручной `Requeue` использует транзакцию вызывающего кода: Courier в ней проверяет
права и допустимость повтора, в том числе запрет повтора истёкшего уведомления.
Hooks остаются наблюдаемостью и не заменяют надёжные изменения состояния.

API: единая OpenAPI-схема, ogen для Go, генерация TS SDK по образцу IAM.
Публичные Go-типы, сервер и клиент находятся в `pkg/api`; `pkg/sdk` создаёт
клиент с сервисным ключом. TS SDK находится в `sdk/ts`, новая админка — в `web`.
Источник Courier использует OpenAPI 3.0.3 и передаётся в ogen без преобразования.

Генерация обязательна для API-контрактов, SDK и типов доступа к БД; ручные
дубли этих типов запрещены. Внутренние структуры реализации — воркеры,
клиенты провайдеров и конфигурация процесса — пишутся обычным Go-кодом.

`make generate` воспроизводит API, SDK и DB-код закреплёнными генераторами.
`make generate-check` сравнивает содержимое и состав generated-файлов. CI также
компилирует SDK, проверяет сервер с PostgreSQL/SMTP и запускает браузерный
сценарий. Отсутствие Docker приводит к ошибке интеграционных проверок.

OpenAPI задаёт тип контейнера запроса, а схему данных конкретного ключа
администратор создаёт в schemapb. Универсальный SDK не может заранее знать
поля будущих ключей: эти данные строго проверяет Courier во время запроса.
Генерация специализированных SDK по настройкам проектов пока не согласована.

## Транспорты

SMTP использует контекстные соединения, TLS/STARTTLS, стабильные Message-ID/date
и MIME multipart/alternative. QUIT после успешного DATA не меняет результат.

WebPush использует [webpush-go v1.4.0](https://github.com/SherClockHolmes/webpush-go/tree/v1.4.0).
Адаптер снимает `mailto:` перед передачей subscriber: библиотека добавляет этот
префикс сама. Тест проверяет VAPID claims и отсутствие открытого содержимого
в зашифрованном запросе. FCM использует сгенерированный Google API client;
повторы классифицируются по [кодам FCM](https://firebase.google.com/docs/cloud-messaging/error-codes).
